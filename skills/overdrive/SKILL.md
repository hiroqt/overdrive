# Overdrive

## Outcome

Select the single best matching installed Overdrive skill and actually follow its current instructions. Keep the user's original request, repository rules, permissions, and evidence boundaries intact.

## Command behavior

- `/overdrive` followed by a task means automatic task-fit routing.
- `/overdrive <skill> <task>` means use that installed skill explicitly; the named skill overrides automatic selection.
- `/overdrive list` lists only domain skills in the installed-skill manifest. `/overdrive help` explains these forms.
- On hosts that namespace plugin skills or use another native invocation syntax, follow the installed host's command name. Keep that host-native form when an unqualified `/overdrive` is unavailable.

## Route filter

1. Read `references/installed-skills.md` and `references/skill-map.md`. Consider only the domain skill names in the installed-skill manifest. If the manifest is missing or empty, inspect the host's available skill list or the neighboring Overdrive skill folders. Never claim an uninstalled skill is available.
2. Classify the requested outcome using the map. For automatic routing, use the request first and inspect only enough current repository context to resolve a real ambiguity or identify relevant stack, instructions, or test tooling.
3. Choose one primary skill. State its name and one short reason when the choice is not obvious. If no installed skill fits, say so and handle the task normally where appropriate.
4. Follow the selected skill's installed `SKILL.md` and any resources it references. Resolve it as a sibling skill folder beside this router in the installed Overdrive bundle or host skill root. If the host exposes a skill-invocation mechanism, use it; otherwise read and follow the installed entrypoint directly. Do not merely name the skill and stop.
5. Adapt only that workflow's relevant steps to the repository, task scope, risk, available tools, and tests. Preserve the selected skill's own approval, read-only, and security boundaries.
6. Do not automatically chain skills. Mention a useful handoff only when another distinct task remains; do not imply it ran.

## Explicit selection

For an explicit skill name, verify it appears in the installed-skill manifest before proceeding. If it is not installed, say which skill is missing and continue only if the user asked for ordinary help beyond that skill. Do not silently substitute a different skill.

For a multi-skill request, select the primary skill that owns the immediate outcome. Keep later steps as optional handoffs unless the user explicitly asks to run a sequence.

## Boundaries

- Use only current conversation and repository context; do not save user preferences or routing history.
- A selection is not proof of execution. Follow the selected procedure and report observed results and limits accurately.
- Do not read every skill entrypoint or run every workflow merely to choose a route.

## Resources

- `references/skill-map.md` defines this collection's routing filter.
- `references/installed-skills.md` is generated by the installer and lists only skills selected for that install.
- `references/evaluation.md` records route and execution checks separately.
